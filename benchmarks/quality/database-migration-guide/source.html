Migrate the events table

Before you start

Verify replica lag before the final rename and keep the previous table for one release.

Record the current row count, table size, and oldest replication replay position. Pause schema changes from other deployments until the migration is complete. The copy process assumes that the source columns and triggers remain stable.

Confirm that the application can read from either table version. Ship that compatibility change before you start the copy. A migration is not safe when the deployment and data cutover must occur in one step.

Procedure

  1. Create the new index without blocking writes.
  2. Start a copy worker that reads rows in primary-key order and commits small batches.
  3. Mirror new inserts and updates through the existing write path.
  4. Compare row counts and checksums for completed key ranges.
  5. Stop the copy worker only after it reaches the live write position. 
CREATE INDEX CONCURRENTLY events_created_at_idx ON events(created_at);

Monitor lock wait time while the index is created. A concurrent build avoids a long write lock, but its final validation still needs a short catalog lock. Cancel and retry during a quieter window if that wait approaches the service timeout.

After the copy catches up, compare aggregates for several independent key ranges. A matching total row count cannot detect a missing row that is offset by an unexpected duplicate.

Rollback

Restore the old view and stop the copy worker. Keep mirrored writes enabled until all application instances confirm the old table is active again.

Do not delete the new table during the incident. Preserve its copy progress and validation records so the team can identify whether the failure came from schema compatibility, replication delay, or the final routing change.
