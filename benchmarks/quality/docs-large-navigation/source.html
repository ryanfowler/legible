Configure request limits

Set a separate limit for each route group to isolate public and administrative traffic. A route group collects endpoints that have the same cost and trust boundary. This design prevents an expensive export request from consuming the capacity reserved for health checks or administrative recovery.

Choose limits from measured service time instead of request count alone. A route that holds a database transaction for two seconds needs a lower concurrency limit than a route that reads a cached status value. Start below the calculated maximum and increase the value only after queue time and memory use remain stable.

Evaluation order

Limits are evaluated before request body parsing. Rejected uploads therefore use minimal memory. The gateway first checks the global connection ceiling, then the route-group concurrency limit, and finally the caller-specific rate policy. It returns the first applicable rejection and does not reserve capacity in later stages.

A request keeps its group reservation until the response body is complete. Streaming responses therefore need a dedicated group when clients can hold connections open for a long time. Background work started by a request must use a separate worker limit.

Defaults

The default group accepts one hundred concurrent requests and a burst of twenty new requests per second. The administrative group accepts ten concurrent requests but does not share capacity with the public group. These defaults suit a small deployment with two gateway processes.

Define an explicit group for uploads, exports, and long polling. Record rejection counts by group and response code. If a group rejects traffic while worker and database use remain low, confirm that requests are not retaining reservations after cancellation.
